# Автоселект по приоритетам и фейловер серверов — отчёт

Дата: 2026-10-31. Задача: shared task board, task-7.
Ветка: `feat/priority-failover`, worktree `/root/MyHome/vpn-client/app-autoselect`
(от `feat/activation-onboarding`, база — Hiddify App 5.3.0).
`app/` и `app-feat/` не трогала; в `main` не мержила; `hiddify-core` (внешняя AAR) не патчила.

## 1. Что сделано

Ядро приоритетов серверов не знает: selector `select` по умолчанию смотрит в `balance`
(round-robin), `lowest` — least-delay. Поэтому «первый живой по порядку подписки» и фейловер
сделаны на стороне приложения — вариант A из `docs/research-hiddify.md` (раздел B), gRPC +
события групп. Ветка ядра не меняется.

**Механика.** После `Connected` приложение:

1. Открывает полный поток групп `OutboundsInfo` (новый `watchAllGroups()` в
   `HiddifyCoreService`) — в нём у каждого сервера свой пинг, в отличие от основного списка,
   где лежит только выбранный. Из группы `select` берутся её leaf-серверы **в порядке
   подписки** — это и есть приоритет (`priorityServersOf`).
2. Сразу пингует все серверы (`urlTest` по каждому тегу), чтобы не ждать штатного интервала.
3. Выбирает gRPC `SelectOutbound(groupTag: "select", outboundTag: <тег>)` первый сервер с
   валидным пингом (`ConnectionConst.isValidDelay`: `0 < delay < 65000`).

**Фейловер/возврат** — в чистой логике `PrioritySelector` (без gRPC и без таймеров, часы
передаются снаружи):

- активный сервер не отвечает **2 оценки подряд** → переключение на первый живой по
  приоритету (следующий живой, а не самый быстрый);
- приоритетный сервер снова отвечает **3 оценки подряд** и с последнего переключения прошло
  **60 с** → возврат на него;
- между любыми автоматическими переключениями — **20 с** кулдауна.

Оценка — раз в **15 с**: пингуется активный сервер и один неотвечающий сервер выше него по
приоритету (по кругу, чтобы недоступный верхний не прятал остальных). Итого: обнаружение
падения ~30 с, возврат после восстановления ~1.5–2 мин, дребезг двух серверов исключён
стриками и кулдаунами.

**Ручной выбор уважается.** Сервер, выбранный в списке прокси руками, не заменяется, пока
отвечает (фейловер с него работает); выбор группы (`lowest`/`balance`, в т.ч. кнопка
«переключиться на самый быстрый») приостанавливает автоселект до следующего подключения.
Смена активного профиля и переподключение сбрасывают состояние.

**Интервал пингов.** `url-test-interval` по умолчанию уменьшен с 10 мин до 2 мин
(`config_option_repository.dart`). Это интервал мониторинга ядра, которым пингуются все
серверы; активный дополнительно пингуется своим 15-секундным таймером.

**UI минимум.** На главной карточке активного прокси рядом с именем сервера — маленький
бейдж «авто» (приоритетный сервер) или «фейловер» (активен не первый по списку). При
фейловере и возврате показывается тост с именами серверов. Строки — ru/en (slang), остальные
локали по фолбэку на en.

## 4. Риски и ограничения

1. **Это управление на стороне приложения, а не приоритеты внутри ядра.** Мгновенности нет:
   реакция на падение — до ~30 с (2 оценки по 15 с) + время `SelectOutbound`; возврат — плюс
   ~1.5–2 мин (3 оценки + 60 с кулдауна). Все пороги — константы в
   `PriorityFailoverNotifier` / `PrioritySelector`, при необходимости выносятся в настройки.
2. **Состояние `Connected` у ядра не про наш выбор.** Ядро считает соединение по группе
   `lowest` (любой живой сервер), поэтому при падении выбранного сервера оно может оставаться
   `Connected` — именно поэтому фейловер нужен в приложении; UI показывает фейловер бейджем и
   тостом, а не «отключено».
3. **Семантика мониторинга ядра принята по коду**: `url-test-interval` = интервал мониторинга,
   `OutboundsInfo` отдаёт полный список и переотправляется на события групп (debounce 1 с).
   Проверено чтением Go-кода v5.3.0; `hiddify-sing-box` в репозитории пуст, поведение самого
   sing-box monitoring не запускалось.
4. **Пинг `0` — «ещё не измерен» (в т.ч. результат из кэша).** Считается невалидным. Чтобы это
   не приводило к ложному фейловеру, после подключения пингуются все серверы сразу, а активный
   — каждые 15 с. Если сервер долго не даёт результат, приложение не переключится на него
   (это «неизвестно живой», а не «живой»).
5. **Ручной выбор определяется эвристикой** (расхождение основного списка с нашим выбором
   позже 8 с после переключения). В редком случае ложного срабатывания автоселект
   приостановится до следующего подключения — это безопасное направление (не воюем с
   пользователем), но лучше проверить на устройстве.
6. **На реальном телефоне не проверялось.** Эмулятор/устройство в этой сессии не
   запускались: проверены компиляция, analyze, unit-тесты и сборка APK; поведение
   `SelectOutbound` в живом туннеле и вид бейджа/тостов надо посмотреть на устройстве с
   реальной подпиской 3x-ui (2–3 сервера, один заведомо мёртвый).
7. **Расход батареи/трафика**: активный сервер и один кандидат пингуются каждые 15 с, все —
   2 мин (маленькие generate_204). При необходимости интервал проб и пороги стоит сделать
   настройкой.
8. **Режимы chain**: для extra security выбор базового сервера в `select` по-прежнему
   осмыслен (hop идёт через `select`); selectable-режим хопа не затрагивается. Если
   пользователь вручную выбирает группу хопа в UI, наш детектор ручного выбора смотрит только
   основную группу — это осознанно вне рамок MVP.
9. **iOS/desktop**: код платформо-независимый, но проверялась только Android-сборка.
10. Лиду: ветка `feat/priority-failover` готова к ревью/мержу; перед выпуском — прогон на
    реальном телефоне с 3x-ui-подпиской и, желательно, запись «до/после» для UI-бейджа.
