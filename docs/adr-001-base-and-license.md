# ADR-001. База клиента и лицензионная развилка

- **Дата:** 31.10.2026
- **Статус:** принято 01.11.2026 в редакции «письмо перед публикацией»; блокирует только публичный релиз
- **Контекст:** новый продукт — платный VPN-сервис на 3x-ui, нужен клиент под
  Android и iOS со встроенными VLESS и AWG, выдачей доступа после оплаты,
  автоселектом по приоритетам, фолбэком и RU→direct.

## 1. Что решили по технике

Владелец выбрал основу — **форк Hiddify App** (Flutter + sing-box). Это быстрый
путь: в форке уже есть подписки, deep-link, TUN-режим, правила маршрутизации,
локализация (в т.ч. `ru`), сборка под Android и iOS. Наш MVP — VLESS из 3x-ui,
AWG отложен на вторую версию.

Технические следствия:

- Нам не нужно писать ядро и TUN с нуля — правим UI и генерируемый конфиг.
- Нужно добавить: активацию по коду (обмен на sub-ссылку), автоселект «первый
  живой по приоритету» (в Hiddify по умолчанию urltest по пингу), включить
  RU→direct по умолчанию, брендинг.
- iOS-сборка требует macOS + Apple Developer Program. Своего Mac нет, но раз
  форк по лицензии обязан быть публичным на GitHub, macOS-раннеры GitHub Actions
  для публичных репозиториев бесплатны — iOS собираем в CI, нужен только Apple
  Developer Program для подписи и распространения.

## 2. Проблема: лицензия Hiddify

`app/LICENSE.md` — это **не чистый GPLv3**, а «Hiddify Extended GNU General
Public License v3» с дополнительными условиями (GPLv3 §7):

| Пункт | Требование | Что значит для нас |
|---|---|---|
| 1 | Публиковать форк на GitHub как форк `hiddify/hiddify-app`, держать в актуальном состоянии | Код нашего клиента будет открыт |
| 2 | Все релизы — только через GitHub Actions | Сборочный конвейер обязан быть в GitHub, не локальный |
| 3 | Атрибуция Hiddify и ссылка на лицензию | Обязательный текст в README/«О приложении» |
| 4 | Запрет вредоносного кода | Ок |
| 5 | Запрет похожих имён/UI (Hiddify, Hidy*, *Ify…) в сторах | Название приложения не должно быть похоже |
| 6 | **NonCommercial: нельзя продавать/рекламировать без письменного согласия** | **Блокер платного сервиса** |
| 7 | ShareAlike: производное — под этой же лицензией | Закрыть код нельзя |

Формулировка п. 6 («use this material for commercial purposes, including selling
and advertising») при платном доступе к сервису читается как нарушение, даже
если само приложение бесплатное. Риск не теоретический: в лицензии прямо
сказано, что при несоблюдении Hiddify вправе требовать удаления приложения из
сторов.

Отдельно: `plugin`-слой sing-box тоже GPLv3 (коммерческое использование не
запрещено, но обязывает открыть производный код), а ядра Xray-core — MPL-2.0
(закрытый код допустим), `amneziawg-go` — MIT.

## 3. Варианты

### A. Получить письменное разрешение Hiddify (быстро)
Написать в Hiddify (GitHub-issue/почта проекта) с описанием продукта и
запросить коммерческое разрешение. Плюс: сохраняем весь объём работ, релиз
быстро. Минус: зависит от чужого ответа; могут отказать или не ответить; условия
могут быть платными.

### B. Свой клиент на sing-box (GPLv3, без NonCommercial)
Свой Flutter-UI + sing-box как ядро (GPLv3 обязывает открыть код клиента, но
**не запрещает** продавать услугу). Лицензия чище Hiddify: снимается п. 6, но
остаётся обязанность публиковать исходники клиента. Плюс: код наш, UI/UX любой,
никакой привязки к чужому форку и его условиям. Минус: UI и все фичи (подписки,
deep-link, правила) пишем сами — 2–3 месяца; App Store и GPLv3 юридически
небезупречны (Apple ToS), но на практике так публикуются многие open-source
клиенты.

### C. Свой клиент на Xray-core (MPL-2.0) + amneziawg-go (MIT)
Закрытый код, без GPL-обязательств, App Store юридически чище. Плюс: полный
контроль, AWG-ядро MIT, VLESS/Reality — MPL. Минус: дольше всего (2–3+ месяца),
и это фактически переписывание того, что уже есть в Hiddify.

### D. Коммерческая лицензия sing-box + форк Hiddify
Не решает проблему: ограничения Hiddify (п. 6, п. 5, п. 1) остаются.

## 4. Предлагаемое решение

1. **Сейчас (до публикации):** продолжаем на форке Hiddify — техническая база
   и пилот для себя/тестеров. Решение владельца 01.11.2026: письмо в Hiddify
   пишем **перед публикацией**, не блокируясь на нём сейчас. Все правки
   (активация, приоритеты, гео, бренд) переносимы на вариант B/C.
2. **Перед релизом** отправляем запрос на коммерческое разрешение (вариант A,
   черновик — letter-to-hiddify.md). Это жёсткий gate: без ответа/разрешения
   публичный платный релиз не выпускаем.
3. **Если разрешения нет** — переходим на **B** (рекомендация): открытый код
   клиента + платный сервис; либо на **C**, если принципиально нужен закрытый
   код. Ветки с нашими фичами переносятся на новую базу (архитектура подписок,
   правила, ядро sing-box — те же).

Рекомендация: B. Причина — сохраняет 80% техработ (архитектура подписок, правила,
ядро sing-box), снимает блокер NonCommercial и не требует переписывать TUN/ядро
с нуля, как в C.

## 5. Последствия

- Даже в варианте A/B наш клиент публикуется как открытый форк — нужно принять,
  что исходники видны. Бренд, серверная часть и списки серверов при этом закрыты.
- Релизы — через GitHub Actions (в любом варианте, где остаётся Hiddify-код).
- Имя приложения выбираем так, чтобы не пересекаться с Hiddify (п. 5).
- До решения по лицензии нельзя публиковать платный сервис в сторах; тестовые
  сборки и пилот на своих устройствах — можно.
